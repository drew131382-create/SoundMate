# SoundMate 音频路由恢复方案

状态：2026-10-05 已实现核心路由恢复及自动故障测试，实机回归待完成。适用于 B 站、浏览器、音乐应用等被 SoundMate 路由的媒体进程。

已实现：统一目标状态与管理队列、进程对象校验、过期任务取消、同步完成资源释放并检查返回值、通话结束刷新有声媒体路由、设备/流格式监听、唤醒恢复、回调与有效缓冲进度监测、最多三次尝试、单应用及全局恢复入口、持久诊断日志、声道布局处理。主动静音与 0% 路由在自动拓扑恢复时保留，重新请求声音时刷新。

尚未实现或验证：独立音频工作进程与阻塞调用隔离、诊断导出、真实微信与设备矩阵回归、50 次通话验收和 5 秒恢复目标。捕获/创建失败时无法凭空保证应用静音，界面会报告控制异常；不会把保存的静音设置改成有声。

## 目标与边界

消除“微信通话结束后，媒体持续无声，只能退出 SoundMate”的故障模式。保留用户保存的应用音量、静音和排除名单。

不能承诺所有 macOS、设备和第三方应用永不出现音频故障。可验收的目标是：在支持的设备上，SoundMate 引起的路由故障能被识别、自动恢复或释放；恢复失败时显示原因与可执行的恢复入口。

首先补充日志并复现：上一次调查未捕获无声发生瞬间，路由问题是主要怀疑方向。B 站保存的增益为 0.1484925（14.85%），通话结束时保留该音量路由是正常需求，本身不证明根因。

## 当前代码中的薄弱点

| 位置 | 行为 | 需要补足的保障 |
| --- | --- | --- |
| AudioTapManager.endCallRouting / removeTapIfIdle | 通话结束仅释放 100%、未静音的路由 | 检查并刷新仍需要保留的媒体路由 |
| AudioTapManager.recreateTapWithRetry | 延迟重建使用之前保存的 PID 列表 | 校验最新需求、进程身份和重建版本，阻止已取消任务重新创建路由 |
| AudioTapManager.activeTaps | 以 PID 判断是否已存在路由 | 检查同一 PID 对应的 Core Audio 对象是否变化 |
| ProcessTapController.invalidate | 在全局队列异步销毁，调用者不等待完成 | 显式完成通知、串行生命周期和清理状态，避免旧、新路由重叠 |
| AudioTapManager.startDeviceChangeListener | 只监听默认输出设备变化 | 覆盖同一设备的采样率、流格式、存活状态变化与睡眠唤醒 |
| ProcessTapController.processAudio | 没有持续的回调健康检查 | 检测回调停滞、无效缓冲和不支持的格式，记录故障原因 |

## 1. 统一路由状态和进程身份

- 用单一管理队列修改路由生命周期，音频回调只处理缓冲并发布线程安全的健康计数。
- 将用户目标状态（音量、静音）与路由实例分开存储。销毁路由不会清除用户设置。
- 为路由记录 PID、Core Audio process object ID、当前宿主标识、输出设备 UID、流格式和版本号。PID 对应对象变化时废弃旧路由。
- 所有延迟任务、重试和清理完成回调携带版本号。应用退出、停止输出、结束通话、设备变化、重置和关闭应用均使相关旧任务失效。
- 重建前重新确认进程存在、当前是否输出、是否仍需音量控制或通话保护，以及是否已有有效路由。不得凭旧 PID 列表恢复路由。
- 状态至少包括：直接输出、创建中、路由有效、释放中、重试等待、故障旁路。创建失败不得报告为路由有效。

## 2. 通话结束执行完整恢复

1. 在确认通话结束后，用一个状态更新撤销通话保护需求、停止 duck 属性恢复循环，并使旧重建任务失效。
2. 重新枚举当前媒体进程，计算最终路由需求，避免逐个撤销保护时丢失本次会话涉及的进程集合。
3. 音量 100%、未静音且无其他需求的媒体进程：完成路由释放，恢复系统直接输出。
4. 音量非 100% 或用户静音的媒体进程：保留设置，验证当前路由；首版在通话结束时主动刷新相关媒体路由，待验证后再减少不必要重建。
5. 刷新按“旧路由停止并完成释放 → 重新校验目标 → 创建新路由 → 验证 I/O”执行。初始化增益、静音和渐变状态必须在启动 I/O 之前完成。

现有通话检测包含 6 秒保持窗口，另有轮询延迟。日志分别记录“最后观察到通话”“确认结束”和“恢复完成”，不能把保持窗口算成恢复动作耗时，也不能承诺挂断后立即恢复。

## 3. 自动发现异常，覆盖设备和应用变化

- 路由存在时启用轻量健康监测；无路由时停用，不长期空转。
- 检查回调是否前进、缓冲是否有效、流格式是否兼容、设备是否存活，以及 process object ID 是否仍匹配。
- 对真实输出中的媒体进程，连续多个采样窗口发现回调停滞才触发恢复；启动阶段留出宽限时间。
- 不把 RMS 为零直接视为故障：视频暂停、静音片段、输入尚未到达都可能正常。用户静音和 0% 增益也不是故障。
- 监听默认输出、当前设备存活、采样率、输出流配置和 Tap 格式；睡眠唤醒后重新枚举。事件集中到管理队列并合并重复重建请求。
- 音频缓冲按实际格式匹配和复制，写入前清空输出缓冲，发现不支持的格式退出当前路由并记录原因，避免继续按固定 Float32 布局解释数据。
- 播放回调活跃不等于扬声器确实出声；这部分必须通过已知测试音和实际设备回归确认，不能只凭 API 返回成功验收。

## 4. 恢复失败时释放异常路由

- 使用有限次数、带退避的重试；达到阈值后进入故障旁路，避免不停重建或重复接管输出。
- 对普通媒体音量控制故障，优先释放 SoundMate 的接管，让系统直接播放。保存原音量设置，界面显示“音量控制暂不可用，已恢复系统播放”。旁路时实际音量可能高于原来 15% 的设定，恢复设计和实机验收必须覆盖这一变化。
- 用户明确静音或音量为 0% 的进程不能自动旁路为有声。保留目标状态，显示控制故障，提供明确的用户恢复操作；不将静音需求悄悄改写为 100%。
- 清理返回值必须检查并记录；清理失败不得直接认定已恢复。正常关闭和“重置音频”复用同一套清理流程。
- Core Audio 调用可能阻塞；单纯把调用移到串行队列并加定时器不能取消阻塞。第二阶段将音频路由放进独立工作进程，主应用监督心跳，超时后结束工作进程以释放其私有 Tap，再决定是否重启。需要单独验证打包、音频权限、崩溃资源回收以及用户静音策略。
- 若系统音频服务本身异常，工作进程结束也不能保证声音恢复。应明确报告该边界，不能默认重启系统音频服务来影响其他应用。

## 5. 日志和恢复入口

- 用可持久检索的结构化日志记录：宿主、PID、process object ID、路由版本、设备 UID、生命周期动作、OSStatus、重试次数与恢复耗时。
- 不录制或保存用户音频。健康计数仅包含回调进度、格式有效性等诊断信息。
- 界面增加单应用“恢复声音”，只重置该应用的媒体路由；现有全局“重置音频”保留。
- 可导出最近一段时间的诊断信息，便于定位无法自动判断的故障。日志不得把系统查询中的失效对象报错直接认定为本次无声根因。

## 实施顺序

1. **第一阶段：生命周期修复。** 补充日志、统一状态、取消过期任务、检查对象身份、等待清理完成、通话结束刷新媒体路由。涉及 AudioProcessManager、AudioTapManager、ProcessTapController。
2. **第二阶段：异常恢复。** 回调健康监测、设备格式事件、有限重试、旁路和恢复入口；验证工作进程隔离，覆盖 Core Audio 阻塞。
3. **第三阶段：发布验收。** 自动故障注入测试、当前电脑的微信与 B 站实机回归，再扩展设备矩阵；通过后替换安装版本。

## 验收标准

以下为拟定标准，尚未执行或通过。

| 场景 | 验收结果 |
| --- | --- |
| B 站 15%、100%、其他非零音量；微信通话前、中、后 | 播放恢复后有声，保存设置不被改写；有效路由无重复播放 |
| 通话中暂停视频，挂断后继续或换视频 | 恢复播放时自动建立正确路由，无持续无声 |
| 通话后关闭再打开 B 站、Helper 重启、同 PID 的音频对象变化 | 旧对象和旧任务失效，新进程绑定正确 |
| 挂断与设备切换、重置、应用退出同时发生 | 不复活已取消路由，每个进程最多一个当前有效路由 |
| 内置扬声器、有线/USB、蓝牙设备；同设备采样率切换 | 自动检查或重建，无需退出 SoundMate |
| 捕获权限拒绝/撤销、设备消失、创建失败、回调停滞 | 明确报告原因；非静音媒体恢复或释放接管，不无限重试 |
| 视频静音片段、暂停、用户静音、0% 增益 | 不误判为持续故障，不擅自解除用户静音 |
| 睡眠唤醒、SoundMate 正常退出或工作进程异常退出 | 清理结果可验证，无由 SoundMate 遗留的异常媒体接管 |
| 连续 50 次接通/挂断，20 次设备切换/重开 | 无持续无声，路由和设备数量不持续增长 |

自动测试使用可注入的 Tap 工厂和可控调度器，覆盖创建/清理失败、旧任务返回、对象更新和输出停启；不要只测试实现内部的字典内容。信号测试检查有效输入到输出的格式、增益、缓冲边界和静音。

恢复耗时的初始目标：故障被确认后 5 秒内完成重建或释放接管，在日志和实机中计时。阻塞调用和系统音频故障单列，不能以超时定时器代替实际释放证明。

## API 依据

- [Apple：CATapMuteBehavior](https://developer.apple.com/documentation/coreaudio/catapmutebehavior)：mutedWhenTapped 在 Tap 被读取期间关闭源进程的硬件直接输出，因此异常转发必须有明确的释放路径。
- [Apple：Capturing system audio with Core Audio taps](https://developer.apple.com/documentation/coreaudio/capturing-system-audio-with-core-audio-taps)：Tap 与聚合设备的创建、销毁及捕获权限要求。
